The tutorial covers what an algorithm is, pseudo-code, correctness proofs, problem-solving tips, running-time complexity with the asymptotic notations $O$, $\Omega$, $\Theta$, $o$ and $\omega$, a running-time comparison table, Stirling's approximation, and three exercises on running times and growth rates. ## Core Concepts
### What Is an Algorithm — PDF pages 4–5
An algorithm (אלגוריתם) is a systematic method that, given some input, performs operations on it and returns an output. The course deals only with deterministic algorithms (אלגוריתמים דטרמיניסטיים): on a given input they always produce the same output.

Whenever the course discusses an algorithm, it really discusses three main things: a step-by-step description of the algorithm, a claim about its complexity, and a claim about its correctness.

The algorithms in the course fall into two main categories. Decision algorithms (אלגוריתמי הכרעה) ask "Is there a way to do ...? If so, what is it?" — for example, is a graph connected, is there a path between two vertices, and what is that path. Optimization algorithms (אלגוריתמי אופטימיזציה) ask "What is the best way to do ...?" — for example, what is the minimum number of steps, or what is a shortest path between two vertices.

### Describing an Algorithm with Pseudo-code — PDF page 6
Pseudo-code (פסודו-קוד) is a common way to describe an algorithm (תיאור אלגוריתם). Writing pseudo-code should be convenient for programmers, since it resembles code in programming languages, but it has no clear and unambiguous grammar rules: it is valid as long as a person who reads it understands it. The slide's example decides whether $y$ is divisible by $x$: if $x = 0$, return false; otherwise set $y \leftarrow y \bmod x$ (written y % x on the slide), and return True if $y = 0$ and False otherwise.

However, an algorithm written in pseudo-code can sometimes look cumbersome and hard to understand. Therefore algorithms may also be described in words, like a story: explain step by step what you do with the input and how you arrive at the output.

### Proving Algorithm Correctness — PDF page 7
Proving algorithm correctness (הוכחת נכונות אלגוריתם) means convincing the reader that the algorithm has no "holes" and that for every valid input it outputs the desired output. There are several common methods; the slide presents two.

A direct proof on an arbitrary input (הוכחה ישירה — על קלט אלמוני) takes some arbitrary input and feeds it to the algorithm. Using mathematical tools, compute a general form of the algorithm's desired output, then show that the algorithm's output is identical to the one computed and proved correct.

A proof by construction, that is, induction on the algorithm's steps (הוכחה בבנייה — אינדוקציה על צעדי האלגוריתם), has three parts. First prove that the initial state of the algorithm is valid. Next prove that every step the algorithm takes, or every new piece of input, keeps the algorithm's state valid. Finally prove that the algorithm stops at the right stage and returns the desired output according to its state. The correctness proof for the diners problem (PDF page 33) is an induction of this kind.

### Problem-Solving Tips: Special Cases, Trivial Solutions and Observations — PDF page 8
Problem-solving tips (טיפים לפתרון בעיות) start with playing with your input: what should the algorithm return in special cases, and which properties do you want it to satisfy? For an algorithm that receives a number, find for which numbers the problem is easier — primes? even numbers? For an array, consider all elements equal, a monotone array, or only positive or only negative elements. For trees, ask what the algorithm should return for a star or a path (חוט), a binary tree, a perfect binary tree, and so on. For general graphs, ask what happens when the graph is a tree, a DAG or a clique.

Next, start from the trivial solution and try to find a weakness in it. Many divide-and-conquer (הפרד ומשול) and dynamic-programming (תכנות דינאמי) algorithms use the trivial solution with a slight improvement that significantly improves the complexity: divide and conquer splits the problem into subproblems that are easier to solve separately, and dynamic programming avoids computing subproblems more than once.

Finally, try to build observations (הבחנות) that advance you toward the solution. Understand the problem: what is the solution made of, and is there a pattern that the solution always contains?

### Problem-Solving Tips: Guessing the Complexity and the Toolbox — PDF page 9
Problem-solving tips (טיפים לפתרון בעיות) also suggest guessing a reasonable complexity for the solution and thinking of an algorithm accordingly. Solutions in $O(n)$ usually pass over the whole input and perform $O(1)$ operations for each element. Solutions in $O(\log n)$ hint at binary search, or at divide and conquer: dividing the problem into subproblems. Solutions in $O(n \log n)$ usually contain some sorting, or a binary search for each of the input elements. One more bound, apparently $O(\sqrt{n})$, hints at divide and conquer that splits the input into $\Theta(\sqrt{n})$ groups, each of size $\Theta(\sqrt{n})$ (the radical sign is missing from the extracted text; see PDF page 9; formula not fully extractable).

If you are completely stuck, go over the "toolbox" (ארגז הכלים) you have. It holds problem-solving methods that the course will teach, such as greedy solutions, divide and conquer and dynamic programming — a solution may use one or more of them — and known algorithms that the course will teach, such as topological sort, maximum flow or DFS. A solution may use these algorithms directly, or adapt one of them to the problem with small changes.

### Big-O, Omega and Theta — PDF pages 10–11
Running-time complexity (סיבוכיות זמן ריצה), which the slides subtitle in English "Running Time Complexity and Asymptotic Order of Growth", is described with asymptotic notation. Big-O: $f \in O(g)$ if and only if there exist $c, n_0 > 0$ such that $0 \le f(n) \le c \cdot g(n)$ for all $n \ge n_0$. Omega: $f \in \Omega(g)$ if and only if there exist $c, n_0 > 0$ such that $0 \le c \cdot g(n) \le f(n)$ for all $n \ge n_0$. Theta: $f \in \Theta(g)$ if and only if both $f \in O(g)$ and $f \in \Omega(g)$.

In words, $O$ bounds $f$ from above by a constant multiple of $g$ from some point $n_0$ onward, $\Omega$ bounds it from below in the same way, and $\Theta$ requires both bounds. A sketch on the slide marks $n_0$ and the curves of $f$ and $g$ to illustrate $f \in O(g)$ (see PDF page 11; diagram not fully extractable).

### Limit Definitions, Little-o and Little-omega — PDF pages 12–13
Limit-based equivalent definitions (הגדרות שקולות) of the asymptotic notations follow, according to the slides, directly from the definition of a limit. Write $L = \lim_{n\to\infty} f(n)/g(n)$, assuming the limit exists (possibly as $\infty$). Then $f \in O(g)$ if and only if $L < \infty$; $f \in \Omega(g)$ if and only if $0 < L$; and $f \in \Theta(g)$ if and only if $0 < L < \infty$.

In addition, there are two "stronger" ways to describe an asymptotic relation (יחס אסימפטוטי). Little-o: $f \in o(g)$ if and only if $L = 0$. Little-omega: $f \in \omega(g)$ if and only if $L = \infty$. The merged median problem later asks for an algorithm whose running time is in $o(n)$, that is, sub-linear (PDF pages 38–40).

### Comparing Running Times — PDF page 14
The running-time comparison table (השוואת זמני ריצה) compares the running times of algorithms of different complexities for different input sizes, assuming that an average computer performs about a million operations per second. Its columns are $n$, $n \log_2 n$, $n^2$, $n^3$, $1.5^n$, $2^n$ and $n!$; its rows are $n = 10$, $30$, $50$, $100$, $1{,}000$, $10{,}000$, $100{,}000$ and $1{,}000{,}000$. Every entry not mentioned below is either less than one second or simply "a lot" (הרבה).

The $n$ column reaches 1 second only at $n = 1{,}000{,}000$. $n \log_2 n$: 2 seconds at $n = 100{,}000$ and 20 seconds at $n = 1{,}000{,}000$. $n^2$: 1 second at $n = 1{,}000$, 2 minutes at $10{,}000$, 3 hours at $100{,}000$ and 12 days at $1{,}000{,}000$. $n^3$: 1 second at $n = 100$, 18 minutes at $1{,}000$, 12 days at $10{,}000$, 32 years at $100{,}000$ and about $10^4$ years at $1{,}000{,}000$. $1.5^n$: 11 minutes at $n = 50$ and about $10^4$ years at $n = 100$. $2^n$: 18 minutes at $n = 30$, 36 years at $n = 50$ and about $10^{17}$ years at $n = 100$. $n!$: 4 seconds at $n = 10$ and about $10^{25}$ years at $n = 30$.

### Stirling's Approximation — PDF page 17
Stirling's approximation (קירוב סטרלינג) helps because the function $n!$ is sometimes hard to work with. It is an asymptotic approximation, $n! \sim \left(\frac{n}{e}\right)^n \sqrt{2\pi n}$, which means that the ratio of the two functions tends to one: $\lim_{n\to\infty} \frac{(n/e)^n \sqrt{2\pi n}}{n!} = 1$. The approximation is very useful for computing limits and for comparing the asymptotic growth (גדילה אסימפטוטית) of functions, as in the limit definitions on PDF pages 12–13. Its proof is beyond the scope of the course; the slide notes that many proofs can be found online for those interested. The slide comes right before the third ordering exercise (PDF page 18), whose list includes a factorial.

### Directed and Undirected Graphs — PDF page 41
A graph (גרף) $G = (V, E)$, in the slides' light introduction to graphs (הקדמה קלה לגרפים), is a set of vertices connected to one another by edges. A graph is called directed (מכוון) if an edge $u \to v$ means that one can go from $u$ to $v$ but not the other way around; in an undirected graph (גרף לא מכוון) there is symmetry. The pursuit game that follows (PDF pages 42–62) is played on an undirected graph, with players moving along edges to adjacent vertices. Its solution builds a bipartite graph (גרף דו-צדדי) whose vertices are split into two sides; the slides call it bipartite because every move leads from one side to the other (PDF pages 49–52).

## Algorithms and Complexity
### Endpoint Sorting with a Counter for the Diners Problem — PDF pages 21–33
Endpoint sorting with a running counter is the full solution (הפתרון המלא) of the diners problem (בעיית הסועדים): given $n$ arrival–departure pairs $p_i = (a_i, b_i)$, find the maximum number of diners present at once. Every change in the number of diners happens at one of the $2n$ interval endpoints. Departure points $b_i$ only decrease it, so the maximum comes right after an arrival point $a_i$; it suffices to track the number of diners after each point and take the maximum (PDF page 21).

Steps: build an array of size $2n$ holding all the interesting points, and mark each point as an entry or an exit of a diner. Sort the array in $O(n \log n)$. Pass over the points in $O(n)$, keeping a counter that always equals the current number of diners. The answer is the maximum value of the counter during the run; the running time is $O(n \log n)$ for sorting plus $O(n)$ for the pass (PDF pages 22–32).

Correctness (הוכחת נכונות) is proved by induction on the pass over the sorted array, given that checking the $2n$ points suffices (PDF page 33). Base: before the sorted array starts there are zero diners; otherwise an entry point would appear to the left of the current point. Step: if the counter is correct before step $i$, an entry point leaves exactly one more diner and an exit point exactly one fewer, so the counter remains correct after step $i$.

### Halving Algorithm for the Merged Median — PDF pages 38–40
The halving algorithm for the merged median problem (בעיית החציון הממוזג) — finding the median of the merge of two sorted arrays of length $n$ — improves on the trivial solution (הפתרון הטריוויאלי). The trivial solution passes over both arrays in parallel and builds the new sorted array, so it takes $O(n)$; the slides then ask whether a sub-linear solution, in $o(n)$, exists.

The optimal solution (הפתרון האופטימלי) compares the two medians $a' = a_{n/2}$ and $b' = b_{n/2}$, assuming without loss of generality that $a' < b'$, and asks what can be said about the elements $a_1, \ldots, a'$ and $b', \ldots, b_n$. Comparing the two medians within a given range of the arrays rules out half of the elements as candidates for the overall median. The algorithm then runs recursively on arrays of size $n/2$ each. The running time is $T(n) = O(1) + T(n/2) = O(\log n)$, so $T(n) \in o(n)$ as required. The extracted slides do not spell out which boundary elements are discarded in each step.

### Game Graph for Rami and Dina — PDF pages 49–52
The game graph for Rami and Dina is a bipartite graph (גרף דו-צדדי) that the solution (הפתרון) builds to represent the pursuit game. One side means it is Rami's turn and the other side means it is Dina's turn. Each side holds a vertex for every possible placement of Rami and Dina; since each of them can be on any of the $n$ vertices of the original graph, each side has $n^2$ vertices. Each vertex thus represents a state of the game.

There is an edge between two vertices if and only if one can move between the two states by some move. After a move on Rami's side it is Dina's turn, and vice versa, so the graph is indeed bipartite. The slides recall this structure before the marking rules: each side represents a different player's turn, each vertex represents a state, and each edge marks that one can move between the states (PDF pages 53–56).

### Marking Winning States — PDF pages 53–56
Winning-state marking colors a vertex of the game graph black (צומת שחורה) if from it Rami can surely force a win. Three observations about the bipartite game graph lead directly to the algorithm. Every vertex that represents a state in which Rami and Dina are on the same vertex is black. A vertex on Rami's side with an edge to a black vertex is itself black, because Rami can make the corresponding move, after which he is guaranteed to be able to force a win. A vertex on Dina's side all of whose edges lead to black vertices is also black, because Dina must make a move from which Rami can force a win.

### Winning-State Algorithm and Running Time — PDF pages 57–62
The winning-state algorithm (הפתרון — אלגוריתם) for the Rami and Dina game first builds the bipartite game graph. It then goes over all vertices that represent a winning state, where Rami and Dina are on the same vertex, and blackens them. Next, every vertex on Rami's side that has an edge to a black vertex is blackened, and every vertex on Dina's side all of whose neighbors are black is blackened. These last two steps repeat until no new vertex is blackened. This completes the preparation: to know whether Rami can force a win, look up the vertex of the starting state and check whether it is black. Returning the best move requires a small change; the slides leave as an exercise why the algorithm does not yet do this and what to change, and the answer is in the slide notes, which are not part of the extracted text.

Running time: each side has $n^2$ vertices, and each iteration goes over all of them. Since every iteration except the last blackens at least one vertex, there are at most $2n^2$ iterations, that is, $O(n^4)$ work in total. The slides ask students to try to prove correctness formally at home.

### Example: The Diners Problem — PDF pages 19–32
The diners problem (בעיית הסועדים): you own a restaurant and have a list of $n$ distinct pairs of the form $p_i = (a_i, b_i)$, representing the arrival and departure times of the diners. Describe an algorithm, with the best complexity you can, for finding the maximum number of diners in the restaurant at any given moment, and prove its correctness and complexity. The slide example is $p_1 = (0,4)$, $p_2 = (2,5)$, $p_3 = (1,7)$, $p_4 = (4,6)$ and $p_5 = (8,9)$.

The solution approach as presented: sort all $2n$ endpoints, each marked as entry or exit, and pass over them with a counter of the diners present, keeping its maximum (algorithm, proof and running time above, PDF pages 21–33). The animation on PDF pages 22–32 shows the counter on the example: 0, 1, 2, 3, 2, 3, 2, 1, 0, 1, 0. At time 4, where $p_1$ leaves and $p_4$ arrives, it goes from 3 down to 2 and back to 3; its largest value, 3, is the maximum number of diners.

### Example: The Merged Median Problem — PDF pages 34–40
The merged median problem (בעיית החציון הממוזג): given two sorted arrays $a_1, a_2, \ldots, a_n$ and $b_1, b_2, \ldots, b_n$, each of length $n$, describe an algorithm for finding the median of the merge of the two arrays. The median element of a set of size $2n$ is defined as the $n$-th element in its order, and all $2n$ elements may be assumed distinct. The illustrations use two arrays of ten cells each, $a_1, \ldots, a_{10}$ and $b_1, \ldots, b_{10}$, also drawn side by side as a single row (see PDF pages 35–38; diagram not fully extractable).

The solution approach as presented: the trivial solution merges the arrays in $O(n)$; the improved solution compares the medians $a' = a_{n/2}$ and $b' = b_{n/2}$, rules out half of the candidates and recurses on arrays of size $n/2$, giving $T(n) = O(1) + T(n/2) = O(\log n)$, which is in $o(n)$ (details above, PDF pages 38–40).

### Example: The Rami and Dina Pursuit Game — PDF pages 42–48
The pursuit game of Rami and Dina (רמי ודינה), presented under the title "A few games" (קצת משחקים), is played on a given undirected graph. Each player stands on a vertex and moves only along edges: on their turn, a player may move to an adjacent vertex or stay in place. Rami's goal is to reach the same vertex as Dina, in which case he wins; Dina's goal is to prevent this at any cost. Describe a polynomial algorithm that, given the graph, the starting positions of Rami and Dina, and who starts, returns whether Rami has a winning strategy and allows answering the best next move in $O(1)$: if Rami starts, it returns his optimal move, then, given Dina's next move, the optimal move again, and so on, like watching two computers play chess. The hint: try to build a graph that describes the game — what special property will it have, how are turns distinguished, and what does each vertex and each edge represent?

A first observation (אבחנה ראשונה) asks whether it is worthwhile for Rami not to move. It is not: if he stays, Dina can also stay and the same state returns, so Rami always moves. The slides admit that this observation does not help much here, though it could probably help in a different approach, and leave as a question for thought which algorithm could use it. The solution builds the bipartite game graph and marks winning states (PDF pages 49–62, above).
